# Shikshaq: context

## In plain words
- Shikshaq is a tuition-finder website for Kolkata. Families browse tutor profiles by subject, board (ICSE, ISC, CBSE and others) and locality, and read free past-paper banks.
- People who use it: students and guardians (parents) who look for tutors and read papers, teachers who list themselves and pay attention to reviews, "checkers" (paper verifiers) and HODs (heads of department) who review question papers, a games team that writes practice questions, reviewers who handle teacher applications, and admins.
- An AI FAQ chatbot (Google Gemini, called through a small server function) answers questions and can suggest approved teachers.
- It runs on a React and Vite website hosted on Vercel, with Supabase as the database, login, file storage and background functions. The live site builds from the `main` branch; a test deployment shares the same Supabase project.
- Papers reach the site in steps: a laptop pipeline outside this repo loads them into the database, student checkers (verifiers) answer them question by question, HODs (heads of department) approve and publish them, and the public site shows them only after a rebuild. A paper with missing pictures or printed pages cannot be given out to checkers.
- The codebase is large (about 1,077 files). Several database and security notes below are open issues the owner should read before changing anything.

## How to run it
- Install: `npm i`. `run-dev.bat` runs `npm install` on every launch (Windows).
- Dev server: `npm run dev` (port 8080; the `PORT` variable overrides it).
- Tests: `npm test` (runs `vitest run --exclude ".claude/**"`); watch mode with `npm run test:watch`.
- Lint: `npm run lint`. Typecheck: `npx tsc -b`. Do not use root `npx tsc --noEmit`; the root tsconfig has `files: []` and checks nothing.
- Build: `npm run build` runs the prebuild generators, then `vite build`, then `tsx scripts/prerender.ts`. It needs live Supabase variables. `npm run build:dev` skips the prebuild hooks.
- Preview: `npm run preview` (CLAUDE.md says port 4180).
- Data scripts: `generate-sitemap`, `generate-blog-stats`, `generate-locality-pages`, `generate-figure-dimensions`, `generate-bank-sql`, `import-bank`, `test:gemini`. The hidden-paper list in `scripts/excluded-papers.ts` must be regenerated after each import.
- Deploy: `npm run push:all` pushes `shikshaq-2.0` to origin and `main` to the test remote. Launch steps are in `docs/LAUNCH.md`: open a PR into `main` with `gh pr create`, then `gh pr merge` (fast-forward). Vercel builds `main`. Rollback tag: `pre-2.0-live`.
- CI: `.github/workflows/ci.yml` runs `npm ci`, `npx tsc -b`, `npm test` and `npx eslint .` on Node 20. There is no build step in CI.
- Setup guides in the root: `GOOGLE_AUTH_SETUP.md`, `LOCALHOST_AUTH_SETUP.md`, `GEMINI_CHATBOT_SETUP.md`, `ADMIN_SETUP_DATABASE.md`, `VERCEL_SETUP.md`. Status and runbook documents are in `docs/`, for example `docs/SUPABASE_RUNBOOK.md` and `docs/GUARDRAILS.md`.

## Main flows
1. Chatbot. `src/components/Chatbot.tsx` answers common questions from a local list after about 300 ms. Otherwise it POSTs `{ message, history }` to `/api/chat` with a 15 second abort, and shows teacher rows with `TeacherCard`. On the server, `api/chat.ts` (`handler`) tries Gemini models in order, each raced against a 15 second timer. If the message has a find-teacher word and a subject keyword, `findMatchingTeachers` queries `subjects`, then `teachers_list` (limit 3), then `Shikshaqmine`. The reply is `200 { response, teachers }`. In development, `vite.config.ts` (`vercelApiDevPlugin`) loads the same handler.
2. Build and prerender. Prebuild generators (`scripts/generate-locality-pages.ts`, `scripts/generate-sitemap.ts` and others) read Supabase and write `src/content/*.generated.ts` and `public/sitemap.xml`. Then `vite build`. Then `scripts/prerender.ts` writes `dist/<route>/index.html` for about 1,700 routes and checks that no question text leaked.
3. Question bank. JSON in `data/question-bank*.json` goes through `scripts/convert-subject-bank.ts`, then either `scripts/import-bank.ts` (service-role upsert into `bank_papers` and `bank_questions`) or `scripts/generate-bank-sql.ts` (writes `supabase/bank-import.sql`). `scripts/generate-blog-stats.ts` writes `src/content/blog-stats.ts`, which feeds `blog.ts`. `generate-blog-nav.ts` writes `blog-nav.ts` for `Footer.tsx`.
4. Subject and board SEO. `src/content/subject-meta.ts` and `subject-seo.ts` feed `SubjectPage.tsx`, `BoardPage.tsx` and `SEOContentBlock.tsx`. `scripts/prerender.ts` reads the same data (around line 634).
5. Locality pages. `scripts/locality-data.ts` reads published, unpaused teachers with the anon key. `generate-locality-pages.ts` keeps subject and area pairs with at least 5 teachers (104 pages). The output feeds the `App.tsx` routes, the sitemap and prerender.
6. Sitemap. `scripts/generate-sitemap.ts` reads `teachers_list`, `papers`, `Shikshaqmine` and `bank_papers` (through `sitemap-bank-urls.ts`, which drops 24 IDs listed in `excluded-papers.ts`). It writes `public/sitemap.xml`, fails if there are fewer than 900 URLs, and exits non-zero when Supabase credentials are missing.
7. Sign-in. Supabase Auth with the Google provider, plus email and password, magic link and reset. `src/lib/auth-context.tsx` checks `check_user_exists` and `check_user_has_password` on sign-up, then calls `signUp`. Sign-in uses `signInWithPassword`. `src/lib/auth-intent.ts` keeps the intended action for 10 minutes. Site URL and redirects switch between localhost:8080 and the Vercel host (see the auth setup guides). The `redirect` value on `/auth`, `/select-role` and `/teacher-terms-agreement` is checked by `src/lib/safe-redirect.ts`.
8. Sign-up and role. `src/pages/Auth.tsx` signs in or up, then reads `profiles`. No role sends the user to `src/pages/SelectRole.tsx` (which upserts `profiles`). A teacher without accepted terms goes to `src/pages/TeacherTermsAgreement.tsx`. Otherwise the user goes to the saved redirect or the home page for their role.
9. Find a teacher. `src/pages/Index.tsx` or `src/pages/Browse.tsx`. Browse prefilters `Shikshaqmine` with an ILIKE query when structural filters are set, filters on the client (`src/lib/teacher-facet-match.ts`), then fetches `teachers_list` by slug in chunks (`src/lib/teachers.ts`). The search index (`src/hooks/useSearchIndex.ts`) is capped at 2,000 teachers and 500 papers.
10. Contact a teacher. `src/pages/TeacherProfile.tsx` shows a WhatsApp button. A signed-out visitor sees `src/components/ContactGateSheet.tsx` and a sessionStorage flag. A signed-in visitor goes to `src/pages/WhatsAppRedirect.tsx`, which records the click and forwards to WhatsApp after 500 ms. The number is read only on tap, through the `teacher_whatsapp_link` function. The heart button in `TeacherCard.tsx` sends signed-out users to `/auth` and otherwise calls `toggleLike`.
11. Reviews. `src/components/TeacherComments.tsx` reads `teacher_comments_public` and `public_profiles`, keeps approved rows plus the viewer's own, and posts into `teacher_comments` with approved set to the inverse of anonymous. Admins publish or remove them in `src/pages/admin/reviews.tsx`.
12. Recommend a teacher. `src/pages/RecommendTeacher.tsx` inserts a pending row in `teacher_recommendations`. An admin marks it contacted, dismisses it, or converts it to an application in `src/pages/admin/reviews.tsx`.
13. Apply to teach. `src/pages/Join.tsx` sets the auth intent, then `src/pages/JoinApply.tsx` (five steps, draft in sessionStorage) uploads the photo, inserts one `teacher_applications` row with status pending, and shows a review screen. An admin decides in `src/pages/admin/approvals.tsx` (RPC `approve_teacher_application`; reject is a conditional update).
14. Read a paper. `src/pages/PastPapers.tsx` or the home shelf leads to `src/pages/PaperResults.tsx`, then the paper page. `/past-papers/:id` shows `PaperReader` for a UUID and `BankPaper` otherwise. A signed-in reader gets the PDF in an iframe after `PaperReader` upserts `paper_reads` and calls the `paper_file_url` RPC. A signed-out visitor sees a blurred page and a sign-in gate. `BankPaper.tsx` (library papers, non-UUID ids) shows questions. Signed-out visitors get two free questions through `bank_paper_questions`, and signed-in users can report one into `question_reports`.
15. Submit a paper. `src/pages/SubmitPaper.tsx` uploads up to a set number of PDF or image files (25 MB each) to the `paper-submissions` bucket, then inserts `paper_submissions` with status pending. On failure it shows a WhatsApp fallback, and files already uploaded stay in the bucket (no cleanup).
16. Checker verdict (paper verifier). `src/pages/Checker.tsx` checks `api.isPaperChecker`, then renders `src/components/checker/VerifyScreen.tsx`. `planAnswer` in `src/lib/checker-drafts.ts` picks pass or fix. `checkerSaveRoute` in `src/lib/checker-save.ts` picks locked, legacy or refuse. The outbox (`src/lib/checker-outbox.ts`) writes to localStorage first, then sends one verdict per paper through `sendVerdict`. `src/lib/checker-verdict-next.ts` builds and parses the `verifier_verdict_and_next` RPC. On a failed send, `src/lib/checker-advance.ts` decides whether to re-read the paper. Definite refusals stop; other errors retry with backoff. Realtime updates come from `src/hooks/usePaperReviewChannel.ts`. A paper on hold should refuse new answers (migration `20261106100000`, not confirmed applied). Undo covers the checker's own answers for 30 minutes (`verifier_undo_last`).
17. Checker pictures and prefetch. `src/lib/checker-pictures.ts` chooses the crop, reusing a warm link from `src/lib/checker-prefetch.ts` or calling the picture RPC, cached by `src/lib/checker-picture-cache.ts`. `prefetchNext` signs up to six upcoming questions in one call. `src/lib/checker-page.ts` allows a whole-page fallback only when the source is marked page-verified. Stored question diagrams come from `verifier_question_diagrams` and show beside the picture (`src/lib/checker-diagrams.ts`).
18. Checker practice. `src/pages/CheckerPractice.tsx` runs an offline round from `src/lib/checker-practice.ts`. It must never reach Supabase and stores nothing.
19. HOD desk. `src/pages/Hod.tsx` checks `api.isHod` and renders tabs from `src/components/hod/` (Needs you, Ready to go live, Live papers, Assignments, Verifiers, Student uploads, History, AI trust, Teacher reviewers). Data comes from `src/lib/hod-api.ts`. `canPublishNow` in `src/lib/hod-publish.ts` gates publishing. `grantHod` and `revokeHod` (`src/lib/hod-admin-actions.ts`) call RPCs and then write an audit entry.
20. Admin approval. `src/lib/admin-approval.ts` calls `admin_*` RPCs. Results go through normalisers in `src/lib/admin-approval-shape.ts`. `changesFromDraft` sends only changed fields. `src/components/admin/approval/ReviewQuestionCard.tsx` edits a question, and `QuestionVersions` shows history and reverts.
21. Admin gate and sections. `src/components/AdminConsole.tsx` `useAdminGuard` selects `admins` by user id (12 second race), then redirects to `/auth` or `/`. `src/pages/admin/index.tsx` shows four tabs (People, Teachers, Logs, System). Admin counts come from `admin_nav_counts` in `src/pages/admin/useAdminSectionCounts.ts`.
22. Games writer. `src/pages/games/WriteQuestions.tsx` (in `src/components/games/`) sends the draft to a 450 ms debounced `GamePreview`, then `Revise`, then `GameView`. Sending calls `api.sendBatch`. `Chapters` saves through `api.saveChapters`. `TryGames` loads `loadQuestionBank`. `src/lib/games/engine/index.ts` `makeGame` tries up to 12 seeds and returns only a puzzle that passes its checker.
23. Errors and stale builds. `src/components/ErrorBoundary.tsx` logs through `logger.error`. It reloads at most once per minute for stale-chunk errors, sharing that budget with the `vite:preloadError` listener in `src/main.tsx` (`claimStaleChunkReload`).
24. Scroll and tour. `src/components/ScrollManager.tsx` (mounted in `App.tsx`) sets manual scroll restoration and keeps positions in sessionStorage. `src/components/ProductTour.tsx` opens on the first visit or on the `shikshaq:open-tour` window event.
25. Paper hand-out. `distribute_unassigned_papers()` (HOD, admin or the service role only) gives papers to verifiers under a 10-paper limit, with class and own-school rules. A paper comes back after 7 days idle (`verifier_return_idle`). HODs can also assign or unassign by hand (`hod_assign_paper`, `hod_unassign`). `hod_held_back_papers` lists papers with missing pictures or printed pages; these sit in a "not ready" list and cannot be assigned.
26. HOD publish. `hod_approve_paper` runs four hard checks (every question checked, pictures present, header complete, scanner junk gone), then the same publish step that `admin_approve_paper` uses. Set-aside questions go live only if the HOD ticks the confirm box (`p_confirm_left_out`). `canPublishNow` in `src/lib/hod-publish.ts` decides whether Publish is enabled. The pipeline never publishes.
27. Question edits. Desk edits send only the changed fields, with the version the editor saw (`buildQuestionChanges` in `src/lib/hod-publish.ts`, `buildEscalationFix` in `src/lib/hod-desk.ts`). A stale version is refused (`40001`). Admin paper editing saves each question 800 ms after the last change (`adminSaveDraftQuestion`); on `40001` that one question reloads. These helpers never trim or re-case question words.
28. Teacher reviewers. An HOD or admin adds a reviewer by email (`hod_add_teacher_reviewer`) and removes one with `hod_remove_teacher_reviewer`. A reviewer reads applications and listed teachers, including phone and email, through `reviewer_list_applications` and `reviewer_list_teachers`, edits through `reviewer_update_application` and `reviewer_update_teacher`, and approves or rejects through `reviewer_approve_application` and `reviewer_reject_application`. Reviewer actions are written to `admin_audit_log`.
29. Admin checker views. The People tab adds a checker by email (`admin_add_checker`) or removes one (`admin_remove_checker`), each with an audit entry. The activity section reads `admin_activity_feed`, and each person's day log comes from `admin_checker_day_log`. Verifier progress reads `admin_team_stats` and `admin_paper_progress`.
30. Visitor signals and copy. `recordSignal` in `src/lib/intent/signals.ts` is the one entry point for meaningful actions. It updates a visitor profile kept on the device only (`shikshaq.intent` in localStorage, `shikshaq.intent.session` in sessionStorage). `resolveIntent` reads it to choose chip labels, the home hero line and call-to-action text. Allowed events go to GA4 and Clarity through `analytics-mirror.ts`.
31. Live paper-review updates. Database triggers (migration `20260928180000`) broadcast changes on the `paper-review` topic (event `activity`). The verify screen uses `usePaperReviewChannel`: when someone else changes the open question, it shows a notice and refreshes the next question.
32. Pipeline to the public site. Papers are loaded into `bank_papers` and `bank_questions` by a laptop pipeline outside this repo. Page pictures go to the public `paper-figures` bucket and the private `audit-figures` bucket. `scripts/prerender.ts` and `scripts/generate-sitemap.ts` read the library at build time, so a paper shows on the site only after a redeploy.

## Who can see what
- **Anonymous visitors (signed out)**: read `public_profiles` (name, role, school or college, grade, avatar) for authors of approved non-anonymous reviews; read approved comments and the `teachers_list` directory minus WhatsApp numbers; read published bank questions only through `bank_paper_questions` (two per paper when signed out; none for unpublished or `needs_review` papers). They can call `site_counts()`, `teacher_whatsapp_link` (returns null), `paper_file_url` (returns null), `check_user_exists` and `check_user_has_password` (rate-limited, needed for sign-in). They can insert teacher applications (email format, 3 per email per 24 hours), guest feedback, `profile_views` rows, `paper_submissions` rows (status pending only), and upload to `hero-images` by prefix. They cannot read `bank_questions`, `read_events` or contact columns.
- **Signed-in users**: read and write their own profile, comments, likes, student or guardian rows, feedback and `paper_reads`. They read full bank paper questions and their own applications (by email), upvote and remove their own upvotes. Teacher recommendations are admin-only.
- **Teachers** (role teacher, matched by profile email): select and update their own `Shikshaqmine` row, but Title, Slug, Sir/Ma'am, EXPANDED and Email ID are reverted by trigger. They read their own contact through `teacher_own_contact()`. They see `profile_views` for their own slug.
- **Checkers (verifiers)**: active paper checkers, including active HODs, use `checker_*` and `verifier_*` RPCs on assigned papers only. They read `audit-figures` only for papers they hold. They have no direct table writes. Legacy checker RPCs were revoked, though the client still names them (see Watch out). The hold migration (`20261106100000`) would also stop answers on a held paper; it is not confirmed applied.
- **HODs**: all checker rights plus HOD RPCs (approve, live edit, assign, registry, trail). They can read the `paper-submissions` bucket, which holds strangers' uploads. An admin counts as a HOD for these checks (`is_hod()`). The automatic hand-out (`distribute_unassigned_papers`) is HOD, admin or service role only.
- **Teacher reviewers**: read applicant and listed-teacher phone and email through definer functions; can edit most listed-teacher fields (not slug, email, contact or pause state). An HOD or admin grants the role.
- **Admins**: `is_admin()` gates admin RPCs, `admin_audit_log` and the admin-only tables. `admin_teacher_contacts()` checks `is_admin()` inside its body. Bank tables are select-only for admins; writes go through admin RPCs with validation.
- **Service role and cron**: pipeline functions, `distribute_unassigned_papers_cron` (every 2 minutes), AI batch functions and `pipeline_update_live_paper`.
- **Nobody on the client**: `read_events`, `read_quota_*`, `pending_role_grants`, backups, `distribution_throttle`, and the `games.*` tables (revoked; RPCs only).
- **Browser-only checks are not security.** `src/components/AdminConsole.tsx` checks admin status in the browser. `Admin` and `HOD` badges are display-only. The study-with role check in `src/lib/studies-with-context.tsx` is browser-only; the code comment says row-level security must enforce it, and that is not visible in the review. Real enforcement is in database policies and RPCs (the RLS checks are not verified in the review).

## Conventions
- Two git remotes (origin for live, and the test remote) must hold identical commits. The working branch is `shikshaq-2.0` (per CLAUDE.md, README and AGENTS.md). Named in 2026: `design-pass-2026-11-05`, `checker-plumbing-2026-11-05`, `main` (live), and the rollback tag `pre-2.0-live`.
- `VITE_` values are public. Secrets are server-only. CLAUDE.md forbids putting passwords under `VITE_` names.
- Generated files (`*.generated.ts`, `blog-stats.ts`, `blog-nav.ts`, `figure-dimensions.ts`, `public/sitemap.xml`) are regenerated, not hand-edited.
- Style: Tailwind tokens from `tailwind.config.ts`; `DESIGN_SYSTEM.md` is the contract; warm neutrals; Geist body and Archivo display; no stock photos; no em or en dashes in reader-facing copy. Copy is plain words with no snake_case and no UUIDs, checked by tests that grep source text. Student checker copy and admin copy are also tested for dashes. Warm grey text was darkened on 6 Nov 2026 for contrast; HANDOFF.md and VISUAL_DIRECTION.md still list the old values. The docs disagree on the display face (Archivo in VISUAL_DIRECTION.md, Geist throughout in VISUAL_LANGUAGE.md).
- Tailwind utilities use brand tokens (`bg-panel`, `text-brand-foreground`, `hsl(var(--foreground))`). `src/components/ui/` primitives use `cva` and `cn` from `@/lib/utils`. A few files hard-code hex colours (alert-dialog, sheet, sonner, paper-cover, ChangeView, AuthHero).
- The `@/*` alias maps to `src`. The app tsconfig is loose (`strict: false`); the node tsconfig is strict.
- ESLint: `no-explicit-any` is a warning; `no-unused-vars` is off.
- File names: PascalCase in most `src/components` folders; kebab-case in `papers/`, `reviews/`, `teacher-review/`, `join/`, `marketing/`, `seo/` and the `*-fake-api.ts` dummies. Components use named exports; a few add default exports (`ErrorBoundary`, `DelayedFallback`, `SEOHead`).
- Injected API pattern: pages and components take API objects as props (`CheckerApi`, `GamesApi`, `HodApi`, `ApprovalApi`, `TeacherReviewApi`). The fakes in `src/dummy/` implement the same interfaces, so real pages run unchanged.
- Most `src/lib` modules have a pure logic layer, a `real*Api` wrapper that calls Supabase, and a fake in `src/dummy/`. Some are pure only, such as `checker-body.ts`; `checker-practice.ts` must never import Supabase.
- RPC wrappers call `supabase.rpc(name as never)`, throw on error and return data. Normalisers are deliberately forgiving (bad values become 0, null or a default). Almost every RPC call uses an `as never` cast because the generated types are out of date. New `hod_*` and `admin_*` functions follow one rule: SECURITY DEFINER, the role checked inside, EXECUTE revoked from `public`, `anon` and `authenticated`, then granted to `authenticated` only.
- Storage access is wrapped in try/catch; keys use the `shikshaq` prefix; the data is device-local only.
- Data fetching uses React Query with scoped keys; module-level caches hold indexes and footer content.
- Gates: `PREVIEW_TOOLS` (`src/lib/preview-tools.ts`), `import.meta.env.DEV`, and `?dummy=1` (with a sessionStorage flag) for dummy mode. Admin and HOD badges are display-only, not authorization.
- Testing: Vitest; markup rendered with `renderToStaticMarkup`; the Supabase client is mocked. Many tests are static and read source files with `readFileSync`. CI has no database, and several tests use relative paths that fail outside the project root. Many migration tests read `supabase/migrations/*.sql` as text and check strings; none of them runs the SQL.
- Supabase names are mixed case and quoted (`"Shikshaqmine"`, `"Classes Taught"`).
- Migrations: `20250122000006` and `20250122000007` each have two files with the same version prefix. Do not replay superseded migrations (see Watch out).
- Dummy and fake modes are only for previews. Dummy leave calls `setDummyMode(false)` and navigates with `?dummy=0`.

## Watch out for
The most important current issues across all the context notes, most serious first. Items 1 to 20 are the older list; items 21 onward come from the 18 Nov notes and are not ranked against them. Lines are given where the notes gave them.

1. **Minors' names and schools are public to signed-out visitors.** The `public_profiles` view is owner-rights and shows name, school and grade of review authors to anonymous users. It is deliberate per the notes, but the owner must confirm it is still intended. `supabase/RUN_THIS_LAST.sql`; `supabase/migrations/20260919120000_restore_public_profiles_view.sql`.
2. **Do not run `RUN_THIS_ONE.sql`.** Its revoke of `get_public_profile_data()` re-breaks the public profile view. It is superseded by `RUN_THIS_LAST.sql`. `supabase/RUN_THIS_ONE.sql`.
3. **Teachers' WhatsApp numbers were readable by anonymous users** (about 148 before the fix). The column revoke `20261012700000` must not be applied until the front end stops naming `whatsapp_number`. Its rollback block restores the leak. `supabase/migrations/20261012700000_revoke_teacher_whatsapp_column.sql`; `src/pages/TeacherDashboard.tsx` line 951 still writes "Email ID", which is revoked for SELECT.
4. **Possible role-promotion path.** `assign_teacher_role_by_email` lets any signed-in user promote another account if the email is on the Shikshaqmine list. The 20260817 file revoked PUBLIC execute but does not say which grants remain, so this is unverified. Partly fixed: `check_existing_users_for_teacher_role` is now admin-only (`20260818120000_lock_down_unguarded_definer_functions.sql`). `supabase/migrations/20250129000000_auto_assign_teacher_role.sql`.
5. **Student reading history is stored with IP hashes and quota enforcement is off.** `read_events` records which papers each person opened with `ip_hash`. The 90-day purge exists only in `RUN_THIS_ONE.sql`, and `read_quota_config.enforcing = false`. Students' uploads are readable by every HOD (`supabase/migrations/20261012196000_hod_read_submission_files.sql`).
6. **Preview passwords are inlined into the public bundle.** Vite inlines `VITE_*` values into the client build. `src/components/PreviewRoleToggle.tsx` lines 30-37 read the preview passwords from `VITE_PREVIEW_*`, and `.env.example` lines 23 and 25 name them under `VITE_` prefixes, which CLAUDE.md forbids.
7. **The Gemini key is documented under a public prefix.** `GEMINI_CHATBOT_SETUP.md` lines 20-22 and 101-102 tell the owner to put the key in `.env.local` as `VITE_GEMINI_API_KEY`, which would expose it in the browser bundle. `api/chat.ts` lines 72-73 and 607 read `VITE_` names on the server. The `.env.example` (lines 11-16) and CLAUDE.md say keep it server-only.
8. **Secret-shaped material is in the project tree.** `.impeccable/live/server.json` line 1 holds a live access token. `SUPABASE_KEY_EXPLANATION.md` lines 61 and 69 hold a service-role-shaped JWT fragment. Treat both as exposed: rotate if they were ever real, and remove them from the repository history. Values are deliberately not reproduced here.
9. **Anonymous users can write to public tables with weak limits.** `teacher_applications` has no TO clause and only a 3-per-email-per-24-hour limit, with no per-IP limit (`supabase/migrations/20250130000005_fix_recommendations_fields_enumeration_spam.sql`). `profile_views` accepts any slug (`supabase/migrations/20260922000000_add_profile_views.sql`). `hero-images` accepts anonymous inserts by prefix (`supabase/migrations/20250129000002_setup_hero_images_storage_bucket.sql`). Not fixed in later notes.
10. **Admin status is checked in the browser.** `src/components/AdminConsole.tsx` line 75 selects `admins` from the client. Real enforcement must be RLS or server side. This was not verified in the review, so confirm the policies before relying on the admin screens to protect data.
